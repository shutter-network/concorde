# The pi adapter spawns one confined process per Run

The `pi` adapter runs `pi` as a **subprocess, one fresh process per Run, inside a container**, and it is configured with **structured fields rather than a command line**. The adapter builds the container invocation itself.

We seriously considered driving `pi` **in-process** through its TypeScript SDK, which is real and capable: `createAgentSession()`, an event stream, and custom tools via `defineTool`. It is more pleasant to program against and removes JSONL parsing entirely. Rejected on exposure. `pi`'s `bash` tool inherits `process.env` wholesale — verified in `dist/utils/shell.js`, which returns `{ ...process.env }` with `agentDir/bin` prepended to `PATH` — so the agent would hold the Gateway's `DATABASE_URL` and could write to every table directly, bypassing the Agent server. That makes [ADR-0010](./0010-the-agent-reaches-the-gateway-over-http.md) decorative and widens [ADR-0011](./0011-the-agent-has-full-read-access.md)'s stated blast radius from "what the API exposes, read-only" to the whole Store, read and write, plus the Gateway's own process. In-process also forecloses [ADR-0004](./0004-runtime-confinement-is-the-deployments-responsibility.md) entirely and couples the Gateway's uptime to `pi`'s.

We also considered having the Operator supply the **raw argv**, so the framework would model nothing about containers. Rejected as too low-level for the common case: a deployment would restate the whole `docker run` line to change a model. Structured fields for `image`, `network`, `model`, `settings`, `models`, `env`, and the mounts cover what deployments actually vary, with a single `extraArgs` for flags we did not anticipate — enough that a missing option never requires forking the adapter. Note this does not violate [ADR-0016](./0016-agent-configuration-is-opaque-to-the-framework.md), which rejects a *runtime-neutral* configuration shape for the framework; a `pi` adapter having `pi`-shaped options is what that ADR prescribes.

## Mounts have three paths, not one

A mount is `{ localPath, agentPath, source }`, where `agentPath` and `source` both default to `localPath`.

- `localPath` — where the Gateway process reads and writes it.
- `agentPath` — where it is mounted inside the container.
- `source` — what the Docker daemon resolves.

All three coincide when the Gateway runs on the host and the Operator is content with matching paths, so a bare string is valid shorthand. They diverge for real reasons: a containerized Gateway needs `source` to be a host path or named volume, because **the daemon resolves the source on the host, not inside the calling container** — get that wrong and Docker silently creates an empty directory, so the agent sees an empty Workspace and nothing errors anywhere.

Named volumes are therefore **not a framework concept**. A deployment that uses one mounts it into the Gateway container too, so the Gateway sees an ordinary directory and the volume is just a value for `source`. The framework never creates volumes and never streams data into them.

Because paths may differ, a handler composing prompt text must use `agentPath` while doing its own file I/O through `localPath`. The framework does not translate; both values are visible.

## Consequences

- **Two mounts, with different lifetimes.** The **Workspace** is shared with handlers. The **agent directory** holds `auth.json` (whose OAuth tokens refresh during a Run), `trust.json`, and `agentDir/bin`, and is touched only by the agent. Mounting whole directories rather than individual files means whatever a future `pi` version persists comes along without us knowing about it.
- **Session directories are per Session**, `<root>/<name>/`, via `--session-dir`. Not tidiness: `--session-id` resolution calls `SessionManager.list()`, which fully parses every `.jsonl` in the directory including each file's entire message text. One flat directory means every Run scans every Session the deployment has accumulated, growing without bound on the hot path. One directory per Session makes that scan see one file.
- **The Agent Runtime creates that directory, not the Gateway.** `SessionManager`'s constructor `mkdir`s its session directory recursively when it persists, which is the path `--session-id` takes, and listing a directory that does not exist returns an empty list rather than throwing — so a first Run in a named Session has nothing to trip over. It is created inside the container, into the bind-mounted Session root, as the Gateway's own uid, which the `--user` requirement below already guarantees. The framework therefore never joins a Session name onto a host path in order to *create* something; the composed invocation still reports the host-side path, for the adapter's debug line alone, because "where is this Session's transcript on my disk" is the question the forgetful-agent failure above is diagnosed with and the container path in the argv does not answer it. What the Gateway *does* create is the Session **root**, once, in the mount check: a bind mount whose source is missing is created by the daemon as `root`, and `pi` running as the Gateway's uid could then not write inside it. A deployment that skips the mount check and has no Session root on disk gets a permissions failure on its first Run — the same bargain as everything else that check catches.
- **Configuration is rewritten before every Run**, not persisted. The Gateway writes `settings.json`, `models.json`, and the system prompt into the agent directory with ordinary `fs`, because it is a plain directory. Combined with [ADR-0003](./0003-prompt-injection-is-an-accepted-risk.md) and ADR-0011, this means **a successful injection cannot durably reconfigure the agent** — every Run restores configuration from the entry point, which is the artifact under version control. The cost is that the agent cannot persist its own settings changes: a `/model` switch survives its Run and is reverted before the next.
- **`pi` validates the Session name, and the adapter does not.** This bullet originally said names were validated at the handler seam, against a transcription of `pi`'s own grammar, and named `user_<id>` as the convention that implies; [ADR-0024](./0024-signal-handlers-receive-only-the-signal.md) records why both are gone, and `--session-id` carries whatever the Handler wrote. **No path-segment check survives here either**, and the reason is not a claim about what `pi` accepts: the Gateway no longer creates anything from the name, and `--session-dir` is a path *inside* a `--rm` container — a name that climbs out of the mounted Session root lands in the container's own filesystem and is gone with it, having touched nothing on the host. Use `--session-id`, never `--session`: the latter only resolves an *existing* session and exits 1 otherwise, where the former creates it if missing, which is exactly ADR-0006's fresh-or-named semantics. A Prompt requesting a fresh Session gets a **generated name** rather than `--no-session`, so the Session file survives for debugging and `Run.session` stays meaningful.
- **Three silent traps in the JSONL output**, all of which the adapter must handle. `--mode json` **exits 0 on model and API errors** — only `mode: "text"` sets a non-zero exit — so success is read from the final assistant message's `stopReason`, never from the exit code. Terminal state is **`agent_settled`, not `agent_end`**, since the latter can be followed by retries or compaction; `agent_settled` is missing from `docs/json.md`'s type union, which is stale. And framing is **strict LF-only**: Node's `readline` is non-compliant because it also splits on U+2028 and U+2029, which are legal inside JSON strings.
- **The container must run as the Gateway's uid and gid.** With bind mounts, files the agent writes are owned by the container's user, so a mismatch leaves handlers unable to read what the agent wrote in the shared Workspace, and vice versa. The shipped Dockerfile and compose file get this right so each Operator does not rediscover it.
- **Startup verifies the mounts rather than inferring them.** The adapter writes a sentinel token into each mount, starts one throwaway container, has it read the tokens back and write its own, then reads those. Failure refuses startup naming the mount. This is deliberately *not* auto-detection: deciding "am I in a container" is a heuristic — `/.dockerenv` is Docker-specific, `/proc/1/cgroup` parsing broke with cgroup v2, Podman and Kubernetes differ — and a wrong guess produces the silent empty-directory failure. One check catches both a wrong `source` and a uid mismatch.
- **The check covers all three mounts, and the agent directory is the one it exists for.** An earlier version of this decision named only the Workspace. That is the *loudest* of the three: the agent reports that a file a handler definitely wrote is not there. The other two say nothing at all. A wrong `sessionRoot` makes every named Session start empty, so each Run succeeds and the agent merely seems forgetful. And a wrong `agentDir` **cannot fail**: `--append-system-prompt` resolves its argument with `existsSync(input) ? readFileSync(input) : input` (verified in `resource-loader.js`), so a missing instructions file makes the agent's instructions the literal string `/…/gateway-instructions.md`. It then runs, answers, and settles successfully, knowing nothing about the Agent server it was supposed to be told about — which makes [ADR-0010](./0010-the-agent-reaches-the-gateway-over-http.md)'s mediation silently unreachable rather than broken. This is a fourth member of the family of silent failures below, and the only one whose fix is a mount check rather than careful reading of the output.
- **The agent should sit on a network containing only itself and the Gateway.** Joining the main compose network also makes Postgres reachable by service name. It would still lack credentials, since `DATABASE_URL` is not in that container's environment, but a dedicated network costs one line of compose and keeps ADR-0011's blast radius structural rather than credential-dependent.
- **`pi` is not a dependency.** It is a container image, so its release cadence never breaks an install, and ADR-0016's passthrough is literal: flags and directories.
