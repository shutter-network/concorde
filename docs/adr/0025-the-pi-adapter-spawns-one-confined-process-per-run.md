# The pi adapter spawns one confined process per Run

> **Superseded in one detail** by
> [ADR-0040](./0040-the-gateway-describes-its-own-http-api.md). The Consequence headed *"The
> Operator now transcribes the Agent server's API by hand"* named a real cost and has been
> paid rather than mitigated: both servers now generate an OpenAPI description of themselves,
> served at `/openapi.json`, and `example/AGENTS.md` points at it instead of restating it.
> What that Consequence says about the *framework* is unchanged, and is the reason this is a
> detail rather than a reversal: the framework still writes no files, still does not read
> `AGENTS.md`, and still cannot see that a copy has drifted. It stopped being the only party
> that knows the routes. Everything else here stands.

The `pi` adapter runs `pi` as a **subprocess, one fresh process per Run, inside a container**, and it is configured with an **Agent Container declaration rather than a command line**. The declaration holds nothing of `pi` in it. `createAgentContainerRuntime` turns an Agent Container plus one function into a **Runtime**, the seam the Signal Worker drives, whose whole contract is `run(prompt)`; the function it takes says what argv follows the image name, what goes on stdin, and how to read the output back. `createPiRuntime` is eleven lines supplying that function. What is `pi`-shaped is the function, and the container declaration, the [Mount Table](./0028-the-mount-table-declares-mounts-and-verifies-nothing.md) it carries and the invocation built from them are shared with any other Agent Implementation run the same way.

We seriously considered driving `pi` **in-process** through its TypeScript SDK, which is real and capable: `createAgentSession()`, an event stream, and custom tools via `defineTool`. It is more pleasant to program against and removes JSONL parsing entirely. Rejected on exposure. `pi`'s `bash` tool inherits `process.env` wholesale — verified in `dist/utils/shell.js`, which returns `{ ...process.env }` with `agentDir/bin` prepended to `PATH` — so the agent would hold the Gateway's `DATABASE_URL` and could write to every table directly, bypassing the Agent server. That makes [ADR-0010](./0010-the-agent-reaches-the-gateway-over-http.md) decorative and widens [ADR-0011](./0011-the-agent-has-full-read-access.md)'s stated blast radius from "what the API exposes, read-only" to the whole Store, read and write, plus the Gateway's own process. In-process also forecloses [ADR-0004](./0004-runtime-confinement-is-the-deployments-responsibility.md) entirely and couples the Gateway's uptime to `pi`'s.

We also considered having the Operator supply the **raw argv**, so the framework would model nothing about containers. Rejected as too low-level for the common case: a deployment would restate the whole `docker run` line to change an image. An Agent Container models what deployments actually vary and requires exactly one field, `image`. `mounts`, `entrypoint`, `networks`, `env` and `containerCommand` are all optional and all defaulted, and `pi` contributes no field of its own at all, only two defaults: `entrypoint: ["pi"]` and `PI_OFFLINE`. A single `extraArgs` carries what we did not anticipate, spliced last among the runtime's own flags so that a later flag wins. That escape hatch used to be **half of one**: it reached the container runtime and nothing reached `pi`. Half of that gap is now closed by modelling rather than by an escape hatch, because `entrypoint` is a field, so an image whose `ENTRYPOINT` is not the agent needs no workaround. The other half stands, recorded as a gap rather than a decision: there is still no way to pass the agent itself a flag the adapter does not model. Note this does not violate [ADR-0016](./0016-agent-configuration-is-opaque-to-the-framework.md), which rejects a *runtime-neutral* configuration shape for the framework; a `pi` adapter having `pi`-shaped options is what that ADR prescribes, and that the `pi` half turned out to need none is a discovery about `pi`, not a change of position.

## The adapter names no paths at all

This section used to define a three-name mount and argue for a startup check that proved each one. Both moved out: [ADR-0028](./0028-the-mount-table-declares-mounts-and-verifies-nothing.md) records the **Mount Table**, which is runtime-agnostic, declares the container's mounts, and deliberately verifies nothing.

What was left here after that was three container paths, which the adapter turned into `--workdir`, `PI_CODING_AGENT_DIR` and `--session-dir <root>/<name>`. All three are gone from the configuration, and the adapter writes none of those arguments:

- **The Workspace.** No `--workdir`, and no field. The image's `WORKDIR` sets the working directory, which is where an image already declares such a thing and where `pi` already looks for `AGENTS.md`.
- **The agent's directory.** No field either: the image declares `ENV PI_CODING_AGENT_DIR`, and something always must. `getAgentDir()` falls back to `join(homedir(), ".pi", "agent")`, and Docker sets `HOME=/` for a uid with no `passwd` entry in the image, which is the ordinary case once the container runs as the Gateway's own uid. The fallback then resolves to `/.pi/agent`, which the agent cannot create. It is a default that never works rather than one that usually does, so leaving it unset is not an option an image has.
- **The Session root.** Gone, and no `--session-dir` is passed at all. `pi` resolves its own session directory, and the Consequences below record what that costs.

Whether those paths are bind mounts, what they are called on the Operator's own disk, and whether the Gateway can reach them at all were already facts the adapter could not get to. It now does not hold the container paths either, and asks the Mount Table nothing.

## Consequences

- **Two directories, with different lifetimes.** The **Workspace** is shared with handlers. The **agent directory** holds `auth.json` (whose OAuth tokens refresh during a Run), `trust.json`, `agentDir/bin`, and now the Sessions as well, and is touched only by the agent. Mounting whole directories rather than individual files means whatever a future `pi` version persists comes along without us knowing about it; a single-file entry in the Mount Table is the exception, and exists for a file the agent must be unable to change.
- **The framework writes no files.** Not `settings.json`, not `models.json`, not a system prompt. The Operator places whatever `pi` should read into the directories they mount, and the adapter performs no filesystem I/O of any kind. Two consequences follow. First, `settings` and `models` were opaque JSON the framework wrote out without reading (ADR-0016), which is pass-through with nothing added, so they are gone from its configuration along with `instructions` and `agentServerUrl`. Second, the **instructions file is gone as a framework concept**: `pi` discovers `AGENTS.md` and `CLAUDE.md` from its working directory and its ancestors (`dist/core/resource-loader.js`), so an Operator places one in the Workspace and the adapter passes no `--append-system-prompt` and knows nothing about it.
- **`model` and `provider` followed them out, into that same mounted `settings.json`.** Verified in pi@0.83.0: `SettingsManager` exposes `defaultModel` and `defaultProvider`, and `main.js` falls back to the saved default when no `--model` is given, so a file the Operator is already placing answers what the two fields answered. The credential can go the same way, as `auth.json` in the mounted agent directory rather than as an `env` entry. The cost is that **nothing refuses a deployment that has no usable model**. A missing model used to make the configuration unconstructable; it is now a Gateway that starts, serves, and fails its first Run, which under [ADR-0017](./0017-failed-runs-are-not-retried.md) is a permanently dead Signal rather than a startup error. That is the same trade [ADR-0028](./0028-the-mount-table-declares-mounts-and-verifies-nothing.md) makes for a mount source, made again for a file the framework is not allowed to read.
- **The Operator now transcribes the Agent server's API by hand.** That file used to be written by the framework, which is the only party that knows the Core's routes, the Signal and Run field shapes, that reads are unscoped and that there is no credential. Accepted, and it is a real cost: every deployment holds a copy of `src/core/routes.ts` in prose and nothing keeps the copies honest. A stale copy produces an agent that simply never asks, which reads as the model being incurious rather than as documentation drift. **This cost has since been paid** ([ADR-0040](./0040-the-gateway-describes-its-own-http-api.md)): the routes describe themselves at `/openapi.json`, the copy in `example/AGENTS.md` is a URL, and what stays in that file is what was never API documentation. The framework still writes nothing and still reads nothing, so the sentence above remains true of the framework; it is no longer true that nothing keeps the copies honest, because there is now one description rather than copies.
- **A durable reconfiguration by injection is prevented by a read-only mount, not by rewriting.** The Gateway used to restore `settings.json`, `models.json` and the system prompt before every Run so that a successful injection could not outlive it ([ADR-0003](./0003-prompt-injection-is-an-accepted-risk.md), ADR-0011). A read-only single-file entry holds the same property by construction, costs nothing per Run, and is what an Operator should reach for. The cost is unchanged in substance: the agent cannot keep its own settings, and a `/model` switch is now dropped rather than reverted.
- **`agentDir/bin` is still writable, still on `PATH`, and still persists between Runs.** This is an open hole rather than a decision, and it is recorded here because the claim that used to stand next to it is gone. `pi`'s shell tool prepends that directory to `PATH` for every child process (`dist/utils/shell.js`), the agent directory survives every Run, and nothing rewrites it. So a Run that writes `agentDir/bin/curl` shadows the real `curl` for every later Run, which is precisely the binary the agent reaches the Agent server with. A read-only mount cannot close it, because installing tooling there is a legitimate use and `trust.json` beside it is `pi`'s to write.
- **Every Session shares one flat directory, and every Run parses all of it.** This bullet used to say the opposite, and the reversal is the price of the section above. `--session-dir <root>/<name>` gave each Session a directory of its own so that the scan below saw one file; with the Session root gone, `pi` resolves the directory itself, `--session-dir` before `PI_CODING_AGENT_SESSION_DIR` before `settings.json`'s `sessionDir` before `<agentDir>/sessions`, and the adapter supplies none of them. The cost is stated rather than hidden. Verified in pi@0.83.0: `SessionManager.list(cwd, sessionDir)` reads and parses every `.jsonl` in that directory, including each file's entire message text, and `--session-id` resolution calls it. The one thing that does shard it shards by the wrong key: observed in a real container, `pi` puts one directory per *working directory* under `sessions`, named after the path, and one `.jsonl` per Session inside it — so with a `WORKDIR` declared once in the image, that is one directory for the whole deployment. Every Run parses every transcript the deployment has ever accumulated, on the hot path, growing without bound, and **the Operator has no way to avoid it**: `sessionDir` moves the directory but nothing shards it. Accepted for what it buys, which is that the adapter holds no filesystem knowledge whatsoever.
- **The Agent Implementation creates that directory, not the Gateway.** `SessionManager`'s constructor `mkdir`s its session directory recursively when it persists, which is the path `--session-id` takes, and listing a directory that does not exist returns an empty list rather than throwing, so a first Run in a named Session has nothing to trip over. It is created inside the container, under the mounted agent directory, as the uid the container runs as. The framework therefore never joins a Session name onto a path of any kind, and no longer reports one either: the composed invocation used to carry the Gateway-side path of the transcript for the adapter's debug line alone, which is the one caller the Mount Table's `gatewayPathFor` ever had, and both went with the Session root ([ADR-0028](./0028-the-mount-table-declares-mounts-and-verifies-nothing.md)). Part of what that line was for is recovered where it is actually read: the `outcome` reader is produced per Run, so it closes over the Session name and a failure says which Session it was, `Session run_x produced no output at all. The container exited with code 2. Its stderr said: …`. **Every mount source is the Operator's to create**: the framework creates nothing, and a source that is not there is refused by the daemon at the first Run.
- **`pi` validates the Session name, and the adapter does not.** This bullet originally said names were validated at the handler seam, against a transcription of `pi`'s own grammar, and named `user_<id>` as the convention that implies; [ADR-0024](./0024-signal-handlers-receive-only-the-signal.md) records why both are gone, and `--session-id` carries whatever the Handler wrote. **No path-segment check survives here either**, and the reason is not a claim about what `pi` accepts: the Gateway no longer creates anything from the name, and the session directory is a path *inside* a `--rm` container, so a name that climbs out of the mounted agent directory lands in the container's own filesystem and is gone with it, having touched nothing on the host. Use `--session-id`, never `--session`: the latter only resolves an *existing* session and exits 1 otherwise, where the former creates it if missing, which is exactly ADR-0006's fresh-or-named semantics. A Prompt requesting a fresh Session gets a **generated name** rather than `--no-session`, so the Session file survives for debugging and `Run.session` stays meaningful. The name is `run_<runId>`, and the **Signal Worker** produces it rather than this adapter: it owns the Run row, so the name goes into `runs.session` in the statement that creates the row, and what used to be a name nothing could trace back to a Run is now the Run's own id. What reaches `--session-id` here is therefore always a string, and the wart this bullet used to record — a generated name being the one thing a Run's own `session` column could not say — is gone ([ADR-0033](./0033-an-agent-is-a-container-and-one-function.md)).
- **Three silent traps in the JSONL output**, all of which the adapter must handle. `--mode json` **exits 0 on model and API errors** — only `mode: "text"` sets a non-zero exit — so success is read from the final assistant message's `stopReason`, never from the exit code. Terminal state is **`agent_settled`, not `agent_end`**, since the latter can be followed by retries or compaction; `agent_settled` is missing from `docs/json.md`'s type union, which is stale. And framing is **strict LF-only**: Node's `readline` is non-compliant because it also splits on U+2028 and U+2029, which are legal inside JSON strings.
- **The container always runs as this process's uid and gid, and that is no longer configuration at all.** It was a Mount Table field, on the argument that ownership is a filesystem fact; [ADR-0028](./0028-the-mount-table-declares-mounts-and-verifies-nothing.md) records why that argument was overruled. `--user uid:gid` is now an argument the Agent Container Runtime always emits, and emits nothing at all on a platform with no uid, which is Windows. `extraArgs` is the documented countermand and works because a later `--user` wins, verified on Docker 29.4.0. The behaviour is kept on evidence rather than on tidiness, verified on the same version: without `--user`, files the agent writes into a bind-mounted Workspace are owned by uid 0, and a Signal Handler running as the Gateway's uid can read them and can delete them but **cannot modify them in place**, where an append fails. That is the worst of the three outcomes, because a handler that reads what the agent wrote and reports on it works, so the deployment looks correct until something tries to edit. `src/pi/container.test.ts:505` asserts exactly that edit. The shipped Dockerfile and compose file line the uids up so each Operator does not rediscover any of it.
- **Every environment value in the logged argv is redacted, with no exceptions list.** The debug line used to hide the values it had reason to think were secret-bearing and print the rest, which is how `PI_CODING_AGENT_DIR` came to be readable in a log. An exceptions list would have to name `pi`'s own variables, and the code that builds the argv is the generic half, which must not know them. So every value is hidden and the names alone survive, `PI_CODING_AGENT_DIR` included. What it costs is the one line that used to say where the agent directory was mounted, which the Operator wrote and can read back out of their own compose file.
- **Nothing about the mounts is verified at startup.** An earlier version of this decision started a throwaway container at boot, wrote sentinel tokens into all three mounts and read them back, on the argument that a wrong mount fails without an error message, a failed Run, or a log line anywhere. [ADR-0028](./0028-the-mount-table-declares-mounts-and-verifies-nothing.md) walks through the four failures it caught and why each stopped being silent or stopped being reachable. Two are worth keeping here because they are `pi`'s own behaviour and would come straight back if the framework ever wrote files again: a wrong mount under the session directory makes every named Session start empty, so each Run succeeds and the agent merely seems forgetful; and `--append-system-prompt` resolves its argument with `existsSync(input) ? readFileSync(input) : input` (verified in `resource-loader.js`), so a missing file becomes the agent's instructions *as a literal path string*, and the Run settles successfully knowing nothing about the Agent server. That second one is why the adapter no longer passes that flag at all.
- **The agent should sit on a network containing only itself and the Gateway.** Joining the main compose network also makes Postgres reachable by service name. It would still lack credentials, since `DATABASE_URL` is not in that container's environment, but a dedicated network costs one line of compose and keeps ADR-0011's blast radius structural rather than credential-dependent. `networks` is a list, because a container can join several, and omitting it leaves the container on the container runtime's default bridge, which is a network nobody chose.
- **`pi` is not a dependency.** It is a container image, so its release cadence never breaks an install, and ADR-0016's passthrough is literal: an image, its mounts and its flags, with the agent's own configuration files never passing through the framework at all.
