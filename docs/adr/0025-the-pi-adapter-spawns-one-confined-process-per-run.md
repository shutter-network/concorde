# The pi adapter spawns one confined process per Run

The `pi` adapter runs `pi` as a **subprocess, one fresh process per Run, inside a container**, and it is configured with **structured fields rather than a command line**. The adapter builds the container invocation itself, out of `pi`'s own flags plus what a [Mount Table](./0028-the-mount-table-declares-mounts-and-verifies-nothing.md) contributes.

We seriously considered driving `pi` **in-process** through its TypeScript SDK, which is real and capable: `createAgentSession()`, an event stream, and custom tools via `defineTool`. It is more pleasant to program against and removes JSONL parsing entirely. Rejected on exposure. `pi`'s `bash` tool inherits `process.env` wholesale — verified in `dist/utils/shell.js`, which returns `{ ...process.env }` with `agentDir/bin` prepended to `PATH` — so the agent would hold the Gateway's `DATABASE_URL` and could write to every table directly, bypassing the Agent server. That makes [ADR-0010](./0010-the-agent-reaches-the-gateway-over-http.md) decorative and widens [ADR-0011](./0011-the-agent-has-full-read-access.md)'s stated blast radius from "what the API exposes, read-only" to the whole Store, read and write, plus the Gateway's own process. In-process also forecloses [ADR-0004](./0004-runtime-confinement-is-the-deployments-responsibility.md) entirely and couples the Gateway's uptime to `pi`'s.

We also considered having the Operator supply the **raw argv**, so the framework would model nothing about containers. Rejected as too low-level for the common case: a deployment would restate the whole `docker run` line to change a model. Structured fields for `image`, `model`, `provider`, `network`, `env` and three container paths cover what deployments actually vary, with a single `extraArgs` for flags we did not anticipate. That escape hatch is currently **half of one**: `extraArgs` is spliced before the image name, so it reaches the container runtime, and there is no way to pass `pi` itself a flag the adapter does not model. Recorded as a gap rather than a decision. Note this does not violate [ADR-0016](./0016-agent-configuration-is-opaque-to-the-framework.md), which rejects a *runtime-neutral* configuration shape for the framework; a `pi` adapter having `pi`-shaped options is what that ADR prescribes.

## The adapter does not know about mounts

This section used to define a three-name mount and argue for a startup check that proved each one. Both moved out: [ADR-0028](./0028-the-mount-table-declares-mounts-and-verifies-nothing.md) records the **Mount Table**, which is runtime-agnostic, declares the container's mounts and the user it runs as, and deliberately verifies nothing.

What is left here is three container paths, which is all `pi` needs of them:

| | what the adapter does with it |
| --- | --- |
| the Workspace | `--workdir` |
| the agent's directory | `PI_CODING_AGENT_DIR` |
| the Session root | `--session-dir <root>/<name>` |

Whether those paths are bind mounts, what they are called on the Operator's own disk, and whether the Gateway can reach them at all are facts the adapter cannot get to. One of them can still be recovered when it matters: the Mount Table's `gatewayPathFor` answers "where is this Session's transcript on my disk", which the debug line below needs and the container path in the argv cannot say.

## Consequences

- **Three directories, with different lifetimes.** The **Workspace** is shared with handlers. The **agent directory** holds `auth.json` (whose OAuth tokens refresh during a Run), `trust.json`, and `agentDir/bin`, and is touched only by the agent. The **Session root** holds one directory per Session. Mounting whole directories rather than individual files means whatever a future `pi` version persists comes along without us knowing about it; a single-file entry in the Mount Table is the exception, and exists for a file the agent must be unable to change.
- **The framework writes no files.** Not `settings.json`, not `models.json`, not a system prompt. The Operator places whatever `pi` should read into the directories they mount, and the adapter performs no filesystem I/O of any kind. Two consequences follow. First, `settings` and `models` were opaque JSON the framework wrote out without reading (ADR-0016), which is pass-through with nothing added, so they are gone from its configuration along with `instructions` and `agentServerUrl`. Second, the **instructions file is gone as a framework concept**: `pi` discovers `AGENTS.md` and `CLAUDE.md` from its working directory and its ancestors (`dist/core/resource-loader.js`), so an Operator places one in the Workspace and the adapter passes no `--append-system-prompt` and knows nothing about it.
- **The Operator now transcribes the Agent server's API by hand.** That file used to be written by the framework, which is the only party that knows the Core's routes, the Signal and Run field shapes, that reads are unscoped and that there is no credential. Accepted, and it is a real cost: every deployment holds a copy of `src/core/routes.ts` in prose and nothing keeps the copies honest. A stale copy produces an agent that simply never asks, which reads as the model being incurious rather than as documentation drift.
- **A durable reconfiguration by injection is prevented by a read-only mount, not by rewriting.** The Gateway used to restore `settings.json`, `models.json` and the system prompt before every Run so that a successful injection could not outlive it ([ADR-0003](./0003-prompt-injection-is-an-accepted-risk.md), ADR-0011). A read-only single-file entry holds the same property by construction, costs nothing per Run, and is what an Operator should reach for. The cost is unchanged in substance: the agent cannot keep its own settings, and a `/model` switch is now dropped rather than reverted.
- **`agentDir/bin` is still writable, still on `PATH`, and still persists between Runs.** This is an open hole rather than a decision, and it is recorded here because the claim that used to stand next to it is gone. `pi`'s shell tool prepends that directory to `PATH` for every child process (`dist/utils/shell.js`), the agent directory survives every Run, and nothing rewrites it. So a Run that writes `agentDir/bin/curl` shadows the real `curl` for every later Run, which is precisely the binary the agent reaches the Agent server with. A read-only mount cannot close it, because installing tooling there is a legitimate use and `trust.json` beside it is `pi`'s to write.
- **Session directories are per Session**, `<root>/<name>/`, via `--session-dir`. Not tidiness: `--session-id` resolution calls `SessionManager.list()`, which fully parses every `.jsonl` in the directory including each file's entire message text. One flat directory means every Run scans every Session the deployment has accumulated, growing without bound on the hot path. One directory per Session makes that scan see one file.
- **The Agent Runtime creates that directory, not the Gateway.** `SessionManager`'s constructor `mkdir`s its session directory recursively when it persists, which is the path `--session-id` takes, and listing a directory that does not exist returns an empty list rather than throwing — so a first Run in a named Session has nothing to trip over. It is created inside the container, into the mounted Session root, as the user the Mount Table runs the container as. The framework therefore never joins a Session name onto a host path in order to *create* something; the composed invocation still reports the Gateway-side path, for the adapter's debug line alone, because "where is this Session's transcript on my disk" is the question the forgetful-agent failure above is diagnosed with and the container path in the argv does not answer it. **The Session root itself is the Operator's to create**, along with every other mount source: the framework creates nothing, and a source that is not there is refused by the daemon at the first Run.
- **`pi` validates the Session name, and the adapter does not.** This bullet originally said names were validated at the handler seam, against a transcription of `pi`'s own grammar, and named `user_<id>` as the convention that implies; [ADR-0024](./0024-signal-handlers-receive-only-the-signal.md) records why both are gone, and `--session-id` carries whatever the Handler wrote. **No path-segment check survives here either**, and the reason is not a claim about what `pi` accepts: the Gateway no longer creates anything from the name, and `--session-dir` is a path *inside* a `--rm` container — a name that climbs out of the mounted Session root lands in the container's own filesystem and is gone with it, having touched nothing on the host. Use `--session-id`, never `--session`: the latter only resolves an *existing* session and exits 1 otherwise, where the former creates it if missing, which is exactly ADR-0006's fresh-or-named semantics. A Prompt requesting a fresh Session gets a **generated name** rather than `--no-session`, so the Session file survives for debugging and `Run.session` stays meaningful.
- **Three silent traps in the JSONL output**, all of which the adapter must handle. `--mode json` **exits 0 on model and API errors** — only `mode: "text"` sets a non-zero exit — so success is read from the final assistant message's `stopReason`, never from the exit code. Terminal state is **`agent_settled`, not `agent_end`**, since the latter can be followed by retries or compaction; `agent_settled` is missing from `docs/json.md`'s type union, which is stale. And framing is **strict LF-only**: Node's `readline` is non-compliant because it also splits on U+2028 and U+2029, which are legal inside JSON strings.
- **The container must run as the Gateway's uid and gid**, and that is the Mount Table's to arrange rather than this adapter's. With bind mounts, files the agent writes are owned by the container's user, so a mismatch leaves handlers unable to read what the agent wrote in the shared Workspace, and vice versa. The shipped Dockerfile and compose file get this right so each Operator does not rediscover it.
- **Nothing about the mounts is verified at startup.** An earlier version of this decision started a throwaway container at boot, wrote sentinel tokens into all three mounts and read them back, on the argument that a wrong mount fails without an error message, a failed Run, or a log line anywhere. [ADR-0028](./0028-the-mount-table-declares-mounts-and-verifies-nothing.md) walks through the four failures it caught and why each stopped being silent or stopped being reachable. Two are worth keeping here because they are `pi`'s own behaviour and would come straight back if the framework ever wrote files again: a wrong Session root makes every named Session start empty, so each Run succeeds and the agent merely seems forgetful; and `--append-system-prompt` resolves its argument with `existsSync(input) ? readFileSync(input) : input` (verified in `resource-loader.js`), so a missing file becomes the agent's instructions *as a literal path string*, and the Run settles successfully knowing nothing about the Agent server. That second one is why the adapter no longer passes that flag at all.
- **The agent should sit on a network containing only itself and the Gateway.** Joining the main compose network also makes Postgres reachable by service name. It would still lack credentials, since `DATABASE_URL` is not in that container's environment, but a dedicated network costs one line of compose and keeps ADR-0011's blast radius structural rather than credential-dependent.
- **`pi` is not a dependency.** It is a container image, so its release cadence never breaks an install, and ADR-0016's passthrough is literal: flags and container paths, with the agent's own configuration files never passing through the framework at all.
